# Spike: storage (PostGIS or DuckDB/Parquet)

**Question:** where should the treated data live so the BFF can answer the app's queries?

**Decision proposed:** DuckDB, as a single read-only file produced by the pipeline and shipped with the BFF. Parquet as the open export of the same data. No database server.

## Setup

- Data: 65,925 vehicle robberies/thefts in São Paulo city from the 2025 and 2026 SSP-SP spreadsheets (data up to 2026-09-30), after D2 dedupe and the D4 classifier, generated by `node/gerar-base.ts`.
- **Allow-list only (D5):** each record has `tipo`, `veiculo`, `familia` (rough brand + model family), `data`, `periodo`, `tipo_dia` and `h3` (resolution 9 cell, no coordinates). No plate, street number, report number or exact location exists in the test base. Period limits for hour → period are **provisional** (0–6, 6–12, 12–18, 18–24); the real limits are still an open decision.
- The four queries the BFF will run, with 50 random filter combinations each (vehicle, incident type, period, weekday/weekend, last 12 months):
  - `zonas`: count per H3 cell (map layer)
  - `area`: count per period inside a cell and its neighbours (area summary)
  - `ranking`: top 20 model families
  - `serie`: monthly series
- DuckDB 1.x through `@duckdb/node-api`, embedded in the Node process. PostGIS 17-3.5 in Docker with indexes on `(veiculo, tipo, data)` and `h3`.
- Both engines return identical counts for every query (checked on all 200 runs).

## Results (two full runs, both consistent)

| Query | DuckDB p50 / p95 | PostGIS p50 / p95 |
|---|---|---|
| zonas | 5.9–6.9 / 18 ms | 4.1–4.8 / 11–15 ms |
| area | 1.8–3.1 / 3–6 ms | 0.4–0.8 / 1–2 ms |
| ranking | 1.4–2.2 / 3 ms | 3.7–5.6 / 5–6 ms |
| serie | 2.6–3.3 / 6–7 ms | 4.6 / 14 ms |

| | DuckDB | PostGIS |
|---|---|---|
| Load 65k rows | 0.18 s | 0.49 s |
| Size on disk | **1.0 MB** (`.duckdb`), **336 KB** (Parquet, zstd) | 7.0 MB (table + indexes) |
| Needs a server | no | yes (container or managed Postgres) |

## Why DuckDB

- **Speed is not the deciding factor.** Every query is under 20 ms on both, and the data changes once a month, so the BFF answers from HTTP cache most of the time (D11).
- **Operation and cost decide.** The pipeline writes one immutable file per monthly release; the BFF opens it read-only. No server to keep awake, no credentials, no migrations, no monthly bill. Rolling back a bad release means pointing to the previous file.
- **Reproducible and open.** The same table exports to a 336 KB Parquet file that anyone can download and query, which fits the "open methodology" differentiator.
- **We don't need PostGIS's spatial engine.** Locations are already H3 cells (D12); "near this address" is `gridDisk` in the app, then an `IN` on cell ids.

## Trade-offs

- PostGIS is faster on point lookups by index (`area`), by about 1–2 ms. Irrelevant at this scale.
- DuckDB is single-writer: fine for a read-only BFF, wrong if we ever need user writes (e.g. storing "report a problem" submissions). Those would go somewhere else (an issue tracker or a small separate store).
- Postgres experience is more common in job ads; DuckDB is the better fit for this data and also a good story for the post.

## Reproduce

```bash
cd spikes/storage/node
node gerar-base.ts      # needs data/raw/VeiculosSubtraidos_{2025,2026}.xlsx
node medir.ts           # needs Docker; starts and removes a local PostGIS container
```

Generated files stay in `data/tmp/` (git-ignored).
